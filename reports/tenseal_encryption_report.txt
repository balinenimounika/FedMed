1. WHY HOMOMORPHIC ENCRYPTION IS USED
-------------------------------------
In Cross-Silo Federated Learning (FL), hospitals compute local model weight or 
gradient updates using private patient MRI scans. Although raw MRI volumes 
never leave the hospital premises, transmitting unencrypted model updates to a 
central server exposes vulnerabilities to model inversion attacks, membership 
inference attacks, and gradient reconstruction leaks. 
Homomorphic Encryption (HE) enables the central server to compute algebraic 
operations (such as addition and scalar multiplication) directly on encrypted 
data (ciphertext) without ever decrypting or inspecting individual hospital updates.

2. WHY CKKS IS SUITABLE FOR FLOATING-POINT MODEL UPDATES
--------------------------------------------------------
The Cheon-Kim-Kim-Song (CKKS) scheme is specifically designed for approximate 
arithmetic over complex and real numbers. Unlike exact schemes (such as BFV/BGV) 
which operate on integers or modular polynomials, neural network weights and 
gradients are floating-point values. CKKS encodes vectors of real numbers into 
polynomial rings and computes additions and multiplications with bounded, 
negligible rounding noise, making it the premier scheme for deep learning models.

3. HOW HOSPITAL CLIENTS ENCRYPT UPDATES
---------------------------------------
- Each hospital client (Hospital 1, 2, and 3) initializes a local TenSEAL CKKS 
  context with polynomial modulus degree N=8192 and coefficient modulus bit 
  sizes [60, 40, 40, 60] with scale 2^40.
- Hospital clients extract their local model or gradient update vectors.
- Using encrypt_update(vector, context), each hospital encrypts its update into 
  a ts.CKKSVector ciphertext.
- The ciphertext is serialized into network bytes and transmitted to the central server.
- The secret key remains exclusively with the authorized clients and is never transmitted.

4. HOW THE SERVER AGGREGATES CIPHERTEXTS
----------------------------------------
- The central server receives only a public evaluation context (is_public = True), 
  which contains Galois and relinearization keys but NO secret key.
- The server receives serialized ciphertexts from Hospital 1, 2, and 3.
- The server executes homomorphic addition directly across the ciphertexts:
      Ciphertext_Sum = Ciphertext_1 + Ciphertext_2 + Ciphertext_3
- To compute the average, the server performs homomorphic scalar multiplication:
      Ciphertext_Average = Ciphertext_Sum * (1.0 / N)
- The resulting object remains a fully encrypted ts.CKKSVector.

5. WHY THE SERVER DOES NOT NEED TO DECRYPT INDIVIDUAL UPDATES
-------------------------------------------------------------
The homomorphic property of CKKS ensures that:
      Dec(Enc(m1) + Enc(m2)) ≈ m1 + m2
      Dec(Enc(m) * scalar)   ≈ m * scalar
Because linear operations can be evaluated purely in the ciphertext space, the 
server performs the entire federated averaging process blindly. Calling .decrypt() 
on the server fails with ValueError ("context doesn't hold a secret_key"), 
guaranteeing mathematical privacy.

6. HOW THE AUTHORIZED PARTY DECRYPTS THE FINAL AGGREGATE
--------------------------------------------------------
- The central server transmits the single aggregated ciphertext to the authorized 
  decryptor (or back to the participating hospital clients).
- The authorized decryptor, holding the private secret key, deserializes the 
  ciphertext and calls decrypt().
- The decrypted vector contains the globally averaged model weights ready for 
  the next federated training round.

9. SECURITY LIMITATIONS
-----------------------
- Homomorphic encryption protects data in transit and during server aggregation.
- It does not prevent poisoned updates from malicious clients (requires Byzantine-robust aggregation).
- It introduces computational and ciphertext expansion overhead compared to plaintext FL.
- In multi-party settings, threshold CKKS or secure key management must be used so 
  no single client holds the unilateral secret key.
